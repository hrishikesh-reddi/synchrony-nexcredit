Section 1

Executive summary

NexCredit AI is a working full-stack prototype that decides credit for applicants with no traditional bureau history, using consented alternative-data signals, document evidence, and a deterministic rules engine — not a trained model. The backend is a Spring Boot 3 service with a PostgreSQL + pgvector store; the frontend is a React 18 workbench with five connected views, a command palette, and an application drawer.

2tiers (Spring Boot + React)
11REST endpoints
5JPA entities
0models trained
Scope statement: the decisioning is deterministic and inspectable. The "stages" in the UI are a workflow visualisation, not autonomous agents. An optional OpenAI-compatible layer can draft explanations/embeddings but is disabled by default (property nexcredit.ai.enabled=false); the demo runs with no external model.
Section 2

Problem statement

Synchrony PS3 asks us to underwrite New-to-Credit and thin-file applicants who lack a bureau footprint. A conventional scorecard returns "no hit" and the application is declined by default. Our system instead:

  • Ingests alternative-data signals (mobile usage, transaction behaviour, social signal) plus income/employment.
  • Runs a fixed, banded scoring function and explains the result with factor-level reasoning.
  • Routes uncertain or high-fraud cases to a human reviewer (never a silent auto-yes).
  • Attaches parsed document evidence and writes every action to an immutable audit ledger.

Hard requirement we honour

A bias guardrail escalates any age-based rejection (<21) to human review instead of auto-declining, so the model cannot reject on age alone.

Section 3

System architecture

Classic three-tier web app. The React SPA calls a stateless Spring Boot API secured by JWT; the API persists to PostgreSQL (with a pgvector extension for semantic evidence search) and parses uploads with Apache Tika.

① React 18 SPA

Workbench (5 views), application drawer, ⌘K command palette, detail drawer. Talks HTTPS with a bearer token via Client.js.

② Spring Boot 3 API

REST controllers → services. Hosts CreditUnderwritingService (deterministic), DocumentEvidenceService (Tika), VectorStore (pgvector), JWT security.

③ PostgreSQL 16 + pgvector

Tables: credit_applications, audit_logs, document_evidence, evidence_embedding(vector). DDL auto-update.

④ Apache Tika 2.9.2

Parses uploaded proofs; text is embedded (remote or local) and indexed for semantic + text search.

Section 7

Backend: the deterministic engine

CreditUnderwritingService.evaluate() is a fixed function of the inputs — no weights are learned, so the same inputs always yield the same decision and explanation. This is what makes it defensible to a regulator.

int total = mobileUsageScore + transactionBehaviorScore + socialSignalScore;

if (mobileUsageScore < 25 || transactionBehaviorScore < 25) {
    decision = REJECTED;  confidence = 92;  fraudRisk = HIGH;
    reasoning = "Low alternative data scores ... below risk thresholds.";
} else if (total > 210 && annualIncome > 300000) {
    decision = APPROVED;  confidence = 88;  fraudRisk = LOW;
} else if (total > 180) {
    decision = APPROVED;  confidence = 76;  fraudRisk = LOW;
} else {
    decision = PENDING;   confidence = 65;  fraudRisk = MEDIUM;  // refer to human
}

// BIAS GUARDRAIL
if (age < 21 && decision == REJECTED) {
    decision = PENDING; confidence = 60;
    reasoning += "[BIAS GUARDRAIL: Age-based rejection escalated to human review.]";
}

// Review routing
if (confidence < 70 || fraudRisk == HIGH || (age < 21 && REJECTED))
    reviewStatus = PENDING_REVIEW;          // human must decide
else reviewStatus = AUTO_APPROVED | AUTO_REJECTED;

Thresholds & bands

ConditionDecisionConfidenceFraudReview
any alt-score < 25REJECTED92HIGHauto (or refer if age<21)
total > 210 & income > 300kAPPROVED88LOWauto
total > 180APPROVED76LOWauto
otherwisePENDING65MEDIUMhuman
Uncertain or high-fraud cases are never auto-approved: they become PENDING_REVIEW and wait for a human in the Review & Governance view.
Section 8

Backend: evidence & vector pipeline

Uploaded proofs are parsed and made searchable. The pipeline degrades gracefully: if pgvector or the embedding API is unavailable, it falls back to token text search.

POST /api/credit/upload (applicationId, file)
  → store file on disk
  → DocumentEvidenceService.extractAndStore()   // Apache Tika parse → textPreview
  → VectorStore.indexEvidence(id, type, name, text)
        → EmbeddingService.embed(text)
             • if NEXCREDIT_AI_ENABLED & key: POST /embeddings (text-embedding-3-small, 1536-d)
             • else: local hashing embed → unit vector (dim 1536)
        → INSERT INTO evidence_embedding (id, source, type, content, embedding vector(1536))
              ON CONFLICT (id) DO UPDATE ...

POST /api/credit/evidence/search { "query": "...", "k": 5 }
  → if available: SELECT ... 1 - (embedding <-> ?::vector) AS score
                   FROM evidence_embedding ORDER BY embedding <-> ? LIMIT k
  → else: fallbackTextSearch()  // token overlap scoring

Six proof types surfaced in the UI

Income · Bank statement · Identity/KYC · Utility · Employment · Tax. Each extracted field is shown next to the decision it supports.

Section 9

Backend: security

  • Auth: AuthController.login issues a JWT (JJWT 0.12.6, HS256, 1h expiry) from in-memory users in nexcredit.security.users.
  • Users: underwriter:underwriter123:UNDERWRITER, admin:admin123:ADMIN, applicant:applicant123:APPLICANT.
  • Transport: stateless JwtAuthenticationFilter; the React client attaches Authorization: Bearer via Client.js.
  • Config safety: secrets come from env (JWT_SECRET, DB_PASSWORD, OPENAI_API_KEY); defaults are clearly dev-only.
The demo auto-authenticates as underwriter on load so the workbench always has a token; no login UI is shown to keep the header clean.

Explainability & comparison

Why this beats a black-box score

Traditional thin-file handlingNexCredit AI
No bureau → silent declineAlt-data → decision or refer, with reasoning
Single opaque cut-offThree outcomes + confidence + fraud band
No human pathUncertain/high-fraud → human review
UntraceableEvery event in audit_logs

Deterministic vs ML (honest trade-off)

Deterministic (shipped)ML (future)
Explainable nowYes — fixed rulesNeeds SHAP/attribution
ReproducibleAlwaysSeed/version dependent
Learns patternsNoYes
Regulatory riskLowRequires governance

The UI renders each decision with its reasoning string, a Risk Radar of the three alt-data signals, a fraud heatmap, and a comparison against a traditional score — so a reviewer sees why, not just what.

Section 13

What was built in this iteration

  • Premium design system (nexcredit-ui.css + AtlasUI.js): KPI cards, sparklines, donuts, trend chart, filter chips, live stream, activity feed, proof-type grid, review queue.
  • Five connected views with live data, charts, and an inline decision preview (select a row → Risk Radar + decision pill + full-decision link).
  • Command palette (⌘K) for instant navigation across applicants and views.
  • Guided application drawer that runs the deterministic decision end to end and shows the DecisionCard.
  • Clean header: brand + search only — removed the API-live indicator, the user badge, and the duplicate nav. A single chip nav sits above the heading.
  • Start application added to the Command Center (same entry as the landing page).
  • Resilient demo: seedData.js mirrors 13 seeded apps + 12 audit entries so the workbench is never empty if the backend is down.
  • Evidence Intelligence: six proof types + semantic (pgvector) / text search.
  • Review & Governance: one-click review queue + filterable audit timeline.
