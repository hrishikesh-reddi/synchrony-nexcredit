Section 1

Executive summary

More than a billion people worldwide are credit invisible: they have no traditional bureau history, so rule-based scorecards either reject them outright or decline to decide. Synchrony's Problem Statement 3 asks us to decide credit for these New-to-Credit and thin-file applicants using consented alternative data, in a way that is fair, explainable, and defensible.

NexCredit AI is a working prototype that does exactly that. It ingests alternative-data signals (mobile usage, transaction behaviour, social signal, income, employment), runs a deterministic, explainable underwriting function, routes anything uncertain or risky to a human reviewer, attaches document evidence (income proof, bank statements, KYC, utility, employment, tax), and writes every action to an audit trail. The outcome is never a black box: each decision ships with its reasoning, factor contributions, and the reviewer who signed off.

Section 2

The problem we are solving

Why thin-file applicants are excluded

  • No bureau footprint. A student, gig worker, or recent migrant has little or no repayment history, so a classic scorecard returns "no hit" and the application is declined by default.
  • One score, no story. Traditional models reduce a person to a single number with opaque cut-offs, offering no path to a yes and no explanation for a no.
  • Unfair proxies. Naive automation can bake in bias (zip code, device, demographics). Inclusion requires guardrails and human oversight.
  • No evidence. Even when alt-data exists, it is rarely tied to the decision or to documents a reviewer can inspect.

What "good" looks like

A New-to-Credit applicant should be able to present consented signals and documents, receive a timely, understandable decision, and — when the case is genuinely uncertain — reach a human reviewer who can approve with confidence and leave a traceable record.

Our design principles

  • Explainability first. Every outcome is computed from visible rules and shown with its factor contributions.
  • Human-in-the-loop. Low-confidence or elevated-fraud cases escalate; the system never silently approves what it is unsure about.
  • Evidence at every step. Decisions reference the documents that support them.
  • Auditability. Each workflow event is logged with who, what, and when.
Section 3

Solution overview

The applicant journey is a single, observable pipeline. A new application is scored, explained, optionally escalated for review, supported by documents, and recorded — all inside one workspace.

1

Intake

Applicant profile + alternative-data signals captured in a guided form.

2

Score

Deterministic weighted scoring across income, behaviour, stability, and fraud.

3

Decide

Approved / Rejected / Refer, with confidence and reasoning.

4

Review

Referred cases reach a human reviewer who approves or rejects.

5

Evidence & Audit

Documents attached; every action written to the audit ledger.

The five stages are a workflow sequence shown to the operator, not five autonomous agents. They share one deterministic engine; nothing acts on its own.

Where the value lands

  • Thin-file applicants get a decision instead of a silent decline.
  • Reviewers get a ranked, evidence-backed queue instead of a raw spreadsheet.
  • Risk and compliance get a complete, queryable audit history.
Section 4

System architecture

A conventional three-tier web app. The backend owns the deterministic decisioning and persistence; the frontend is a read-and-act workbench; an optional local LLM can draft explanations but is off by default so the demo is fully reproducible.

Frontend — React 18

Workbench (5 views), application drawer, command palette (⌘K), detail drawer. Talks to the API over HTTPS with a bearer token.

Backend — Spring Boot 3

REST API for applications, analysis, review, audit, and evidence search. Hosts the deterministic underwriting service and the fraud-routing rule.

Data — PostgreSQL + pgvector

Applications, audit logs, and (when available) vector embeddings for semantic evidence search. Falls back to text retrieval locally.

Evidence — Apache Tika + vector search

Uploaded documents are parsed (Tika), embedded, and searched semantically; text fallback keeps the flow working without a model.

Request flow

StepCallerAction
CreateFrontendPOST /api/credit/applications
AnalyzeFrontendPOST /api/credit/analyze → deterministic score + reasoning
ReviewReviewerPOST /api/credit/review/{id} → APPROVED / REJECTED
EvidenceFrontendPOST /api/credit/evidence/search
AuditBackendGET /api/audit/logs → immutable event ledger

Optional: a local LLM can be enabled to draft plain-language explanations. It is disabled by default; the shipped demo is deterministic and does not require any model.

Section 7

The deterministic decision engine

The engine is a fixed function of visible inputs — no trained weights, no randomness. This is what makes every decision explainable and reproducible.

Signals used

SignalMeaning
Income adequacyAnnual income vs. obligations and cost-of-living
Rent / obligation burdenShare of income committed to fixed obligations
Employment stabilityType and tenure (e.g. salaried vs. student vs. gig)
Mobile usage scoreConsented device/usage signal (0–100)
Transaction behaviour scoreConsented cash-flow regularity (0–100)
Social signal scoreConsented network/identity signal (0–100)
Age & bureau absenceThin-file penalty applied transparently
Fraud riskScore-based LOW / MEDIUM / HIGH routing

How a decision is reached

  • Each signal maps to a banded contribution; bands are documented, not learned.
  • A weighted composite score and a confidence value are produced.
  • High confidence + clean fraud → APPROVED.
  • Clear adverse signal → REJECTED, with the triggering factors named.
  • Uncertain or elevated-fraud → REFERRED to a human reviewer (no silent yes).
Because the logic is deterministic, the same inputs always yield the same decision and the same explanation — a property a real credit desk can defend to a regulator.
Section 8

Alternative-data evidence

Decisions are stronger when they point at documents. Evidence Intelligence organises six proof classes and lets a reviewer search them by meaning, not just by filename.

Income proof

Pay slips / income statements; extracts employer, amount, period.

Bank statement

Cash-flow history; supports transaction-behaviour scoring.

Identity / KYC

ID document; verifies the applicant is who they claim.

Utility bill

Address and stability evidence.

Employment letter

Confirms employment type and tenure.

Tax document

Independent income corroboration.

Pipeline

An uploaded file is parsed with Apache Tika, split into chunks, embedded (pgvector when available), and indexed. Semantic search runs the same embeddings; if the vector store is unavailable the system falls back to text retrieval so the feature never breaks. Each extracted field is shown next to the decision it supports.

Section 9

Fraud routing & human review

Fraud-risk routing

A score-based prototype classifies each case LOW / MEDIUM / HIGH. Elevated risk routes the case to review and lowers auto-approval likelihood. This is prototype routing, not device-fingerprint, graph, or velocity fraud detection — those belong in the production evolution.

Human-in-the-loop

Referred cases appear in the Review queue. A reviewer approves or rejects with one click; the note and outcome are written to the audit ledger. A human always owns the final call on anything the engine is unsure about.

Audit trail

Every analysed, reviewed, and escalated event is appended to an immutable log: applicationId, decision, reasoning, timestamp. The Review & Governance view filters this timeline so a compliance officer can reconstruct any decision in seconds.

Section 10

Truthfulness & scope

We state plainly what this system is and is not, because a credit tool must not overclaim.

TrueNot true
Deterministic, explainable underwritingA trained production risk model
One visualised workflow (5 stages)Autonomous multi-agent runtime
Local fallback, no model requiredRemote LLM always-on
pgvector when present, text fallbackVector search guaranteed everywhere
Score-based fraud routingDevice / graph / velocity detection
The "stages" in the UI are a workflow visualisation for the operator. They are not independent agents and nothing executes without the deterministic engine and (where required) a human reviewer.

Model governance

Explainability service

Per-decision SHAP-style attributions behind the deterministic trace.

Consent & privacy

Granular alt-data consent, retention, and right-to-explanation flows.
